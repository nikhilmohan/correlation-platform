AI/ML Alarm Correlation Platform — Core IP MVP

Solution Design & AI-Led Build Specification · Version 0.2 (MVP) · Domain: Core IP network fault correlation

Revision note (v0.1 → v0.2)

  • Pattern Miner Service reduced to PrefixSpan model execution and configuration only (PySpark). It no longer owns RCA, codebook reconciliation, explainability, the Pattern Store, or lifecycle.
  • Pattern Manager Service added — owns pattern status/lifecycle, RCA, reconciliation, explainability metadata and the Pattern Store. The ML step is now cleanly separated from pattern management.
  • Tech stack split by workload: graph/simulation and ML services run Python (Simulator, Trail Builder, Codebook Generator on networkx; Noise Filter on scikit-learn; Pattern Miner on PySpark); API/streaming/state services run Spring Boot (Topology, Knowledge, Enrichment, Pattern Manager, Correlation Engine); UI on Angular 20.
  • New patterns.mined topic and PatternMinedEvent payload connect Miner → Manager.

1. Problem Statement

Telco networks emit very high volumes of alarms. A single underlying fault (a fiber cut, a line-card failure, an optical amplifier loss) propagates upward through the physical, link, routing, transport and service layers, producing tens to thousands of alarms for one root cause. Network Operations Centres (NOCs) are flooded with these symptomatic alarms, struggle to identify the true root cause, and waste effort on duplicate incidents.

Pure rule-based correlation is brittle and unmaintainable at network scale; pure unsupervised mining on raw alarm streams produces noise because it lacks network structure. The platform therefore takes a hybrid, topology-grounded approach: it uses the network topology to constrain where correlation can happen, combines a model-derived codebook (works from day one, covers rare critical faults) with data-driven pattern mining (learns the messy real-world behaviour), and keeps a human-in-the-loop for pattern approval and incident correction.

This document specifies an MVP covering the Core IP domain only, exercised against a synthesized but grounded topology and alarm dataset, built as Docker-based, event-driven microservices.

2. Goals & Non-Goals

Goals (MVP)

  • Ingest a synthesized multi-layer Core IP topology and build correlation trails (spatial clusters) plus a codebook (fault → symptom signatures) using domain knowledge.
  • Discover correlation patterns from historical alarms using DBSCAN noise filtering and PrefixSpan sequence mining, with structural + temporal RCA and explainability.
  • Allow a human to approve/reject discovered patterns.
  • Perform real-time correlation of live alarms against approved patterns and the codebook, tagging a root cause and child alarms.
  • Provide an Angular UI for topology/trail visualization, pattern review + explainability, configuration, and correlation effectiveness stats.
  • Be measurable: because synthetic data carries injected ground-truth root causes, report alarm-reduction ratio and RCA accuracy.

Non-Goals (MVP)

  • Other domains (RAN, Transport, Mobile Core) — the design must generalize but only Core IP is built.
  • Production-grade HA/scale, multi-tenancy, real OSS connectors.
  • Redundancy/protection-aware propagation (FRR, ECMP) — deferred; templates assume straight-up propagation initially.
  • Automated retraining / closed-loop feedback execution (the feedback path is captured but not auto-applied).
  • Schema registry — replaced by a shared canonical event model library (see §7).

Constraints

  • Open-source, permissive licenses only (Apache-2.0 / BSD / MIT / PostgreSQL). No GPL/AGPL/BSL/source-available components.
  • Event-driven via Apache Kafka; persistence via PostgreSQL; topology graph via Apache AGE (Postgres extension), abstracted inside the Topology Service.

3. Solution Overview

Core concepts

  • Topology graph — a typed, multi-layer model (fiber → IP link → IGP adjacency / LSP → VPN service), assembled from synthesized source data.
  • Trail — an undirected, policy-bounded cluster of connected objects that may correlate together. A device belongs to multiple overlapping trails (per LSP path, per SRLG, per IGP area).
  • Codebook — a compiled matrix of candidate root cause → predicted symptom signature, generated by running forward-propagation templates from each enumerated fault origin over the graph. Each scenario is tagged to the trail(s) it occupies.
  • Pattern — a data-mined, ordered alarm sequence (PrefixSpan) with support/confidence/lift, RCA, and timing stats; lifecycle draft → approved → deprecated. Mining is performed by the Pattern Miner; all status, RCA and metadata are owned by the Pattern Manager.
  • Two pattern producers, one consumer — the codebook (model) and the approved patterns (data) both feed the real-time correlation engine.

Three phases

  1. Phase 1 — Topology & scopes (offline): ingest topology → build trails → compile codebook → visualize.
  2. Phase 2 — Learning (offline): enrich + deterministic-filter alarms → DBSCAN noise removal → PrefixSpan mining → RCA + codebook reconciliation + explainability → human approval.
  3. Phase 3 — Real-time correlation (online): enrich + filter live alarms → stateful match/decode against approved patterns + codebook → score + conflict-resolve → tag RCA + child alarms → stats.

4. Architecture

4.1 System architecture

Every X → Y that is not a topic label is an API/event read. The Topology Service is the single owner of the graph; Trail Builder, Codebook Generator, Pattern Manager and Correlation read trails/codebook via API or event, never the graph directly.

4.2 End-to-end flow

4.3 Event-driven design & canonical event model

No schema registry is used. Instead, a shared canonical event library (a versioned package imported by every service) defines:

  • A common envelope (id, type, schemaVersion, occurredAt, source, traceId, payload).
  • A set of specialized payloads (AlarmEvent, TopologyChangedEvent, TrailsBuiltEvent, CodebookGeneratedEvent, TransactionEvent, PatternMinedEvent, PatternDiscoveredEvent, PatternApprovedEvent, CorrelationResultEvent).

Governance without a registry: the library is the single source of truth, versioned with the repo; schemaVersion in the envelope guards compatibility; consumers reject envelopes with an unknown major schemaVersion.

4.4 Data stores

  • Apache AGE (Postgres extension) — topology graph; accessed only through the Topology Service.
  • PostgreSQL — alarm store, pattern store (owned by the Pattern Manager, with lifecycle), incident/correlation-group store, knowledge store (templates, policy, params). Logical separation by schema.
  • Apache Kafka — inter-service event bus.

4.5 Cross-cutting concerns

  • Identity binding (critical): synthesized alarms MUST reference the same managedObjectId values used by the topology graph, so enrichment can map alarm → object → trail. Define the ID scheme once in the canonical library.
  • Topology versioning: every topology load creates a snapshotId; trails and codebook reference the snapshot they were built from.
  • Idempotency: Kafka is at-least-once; consumers key on eventId/alarmId and dedupe.
  • Observability: structured JSON logs + Prometheus metrics (Apache-2.0). Dashboards rendered in the Angular UI or Apache Superset (avoid AGPL Grafana).
  • Error handling: dead-letter topic per consumer; poison messages routed there, not dropped silently.

5. Topology Graph Model

Site & placement (domain-agnostic): a Site object type represents a geographic site; each device is placed in a site via a LOCATED_AT relation (device LOCATED_AT Site). Sites carry geo attributes (name, latitude, longitude, region). The UI organizes topology by site and expands into the site's device-level graph. Site and LOCATED_AT are reused by every domain.

Device & connection attributes: nodes and edges carry an extensible attributes map of descriptive properties — well-known device keys vendor, model, equipmentType, role, capacity; connection keys linkType, capacity, protectionRole. These are descriptive (not identity) and may feed Noise Filter features / Trail Builder / Codebook policy. The attribute catalogue per domain is authored in the Knowledge Service.

Domain-agnostic typing: the object-type and edge-relation names below are the Core IP domain's vocabulary (authored in Knowledge). Other domains (fixed access, RAN, transport) define their own object-type/relation vocabulary in Knowledge and plug in without changing the event model or services — see architecture.md → "Domain extensibility". The managedObjectId scheme <objectType>:<id> is generic.

Fault-origin types (authored, Core IP): Fiber, LineCard, Port, Node. (IPLink, Adj, LSP, VPN are effects, not origins.)

Propagation templates (authored, generic, per edge type):

RIDES_ON        : fault(Fiber)        => LinkDown(IPLink)
HOSTED_ON       : fault(LineCard)     => PortDown(each Port);  PortDown => LinkDown(its IPLink)
ADJACENCY_OVER  : LinkDown(IPLink)    => AdjDown(IGPAdjacency)
TRAVERSES       : LinkDown(IPLink)    => LSPDown(LSP head-end)
SERVES          : LSPDown(LSP)        => ReachabilityLoss(VPN)
MEMBER_OF       : co-failure grouping (fate sharing)

Trail policy (authored): trail = transitive closure over the dependency edges from each seed, bounded by IGP area; all links in one SRLG join the same trail. Trails overlap; a device may belong to many.

6. Microservice Specifications

Each spec is written as a directive build brief for an AI coding agent. Standard expectations for all services: containerized (Docker), import the shared canonical event library, expose /health and /metrics, structured logging, config via environment variables, unit + contract tests, README with run instructions.

6.1 Simulator Service

Responsibility: Generate a grounded synthetic Core IP topology and labeled alarm streams (historical + live); replay them onto Kafka. Doubles as the evaluation harness (ground-truth labels).

Build instructions:

  • Generate a realistic Core IP topology: PE/P/RR/peering nodes, line cards, ports, IP links, IGP adjacencies, LSPs over link paths, VPN services over LSPs, fiber spans with SRLG groupings. Make size configurable (e.g., 10–200 nodes).
  • Assign stable managedObjectIds shared between topology and alarms (per §4.5).
  • Generate a domain-grounded topology snapshot file and upload it to the Topology Service's ingestion API (not a Kafka event). Generation is domain-parameterized (a reusable engine + a domain pack; Core IP is the MVP pack).
  • Generate labeled fault scenarios: inject known root cause → cascade (e.g., fiber cut → LinkDown ×2 → AdjDown → LSPDown → VPNloss) with configurable timing jitter; add background noise (flapping, self-clearing transients, chatty standing alarms, coincidental unrelated alarms). Persist the ground-truth label (which root cause, which children) for evaluation.
  • Replay modes: history (batch onto alarms.history) and live (streamed onto alarms.live with wall-clock pacing).

Technologies: Python; networkx (BSD) for topology generation; confluent-kafka / kafka-python (Apache/permissive); Pydantic for the event models (shared canonical event library).

Integrations: Produces alarms.history, alarms.live; uploads the topology snapshot file to the Topology Service ingestion API (client built against Topology's published OpenAPI). Reads scenario configs from local files or Knowledge Service.

Acceptance criteria:

  • Produces a valid, internally consistent topology snapshot with shared IDs.
  • Can emit a labeled fiber-cut scenario whose cascade matches the propagation templates, plus ≥3 noise classes.
  • Ground-truth labels retrievable for evaluation.
  • History and live replay both demonstrably land on the correct topics.

6.2 Topology Service

Responsibility: Sole owner of the topology graph. Ingests a topology snapshot file via a published ingestion API, lifts records into the typed multi-layer graph in Apache AGE, versions snapshots, exposes query APIs, emits topology.changed.

Build instructions:

  • Expose a topology ingestion API (OpenAPI 3.1) accepting a topology snapshot file (the versioned topology-file schema); apply lifting rules (flat link/adjacency/LSP/VPN/fiber records → typed nodes + typed edges per §5).
  • Persist into AGE, abstract AGE entirely behind a service API (openCypher internally; callers never touch the DB).
  • Maintain snapshotId versioning; keep current + previous snapshot.
  • Expose REST/gRPC: get node/edge, get neighbors, traverse by edge types (bounded), resolve managedObjectId → object + layer, list objects by type.
  • Emit topology.changed with the new snapshotId.

Technologies: Java (Spring Boot); PostgreSQL + Apache AGE; openCypher.

Integrations: Ingests the topology snapshot file via its published ingestion API (producers upload against that OpenAPI); produces topology.changed; serves Trail Builder, Codebook Generator, Enrichment, UI.

Acceptance criteria:

  • A snapshot with N nodes/edges loads and is queryable; AGE is never exposed outside the service.
  • Bounded traversal by edge types returns correct closures (verified against the synthetic topology).
  • managedObjectId resolution returns the object and its layer.
  • Re-ingesting a changed topology creates a new snapshotId and emits topology.changed.

6.3 Knowledge Service

Responsibility: Authoritative store for domain knowledge — propagation templates, fault-origin types, trail policy, and Phase-2 model parameters (DBSCAN params, session-window gap, min-support, etc.). Versioned, served via API; backed by config UI.

Build instructions:

  • Model templates/policy/params as versioned, validated records in PostgreSQL.
  • Expose CRUD + versioned read APIs.
  • Validate edits (e.g., a template must reference a known edge type).
  • Emit knowledge.updated so dependent services can refresh.

Technologies: Java (Spring Boot); PostgreSQL.

Integrations: Serves Trail Builder, Codebook Generator, Pattern Miner, Pattern Manager, Noise Filter, UI config page; produces knowledge.updated.

Acceptance criteria:

  • Templates, origin types, trail policy and model params are CRUD-able and versioned.
  • Invalid edits are rejected with clear errors.
  • Consumers can fetch a specific version; knowledge.updated is emitted on change.

6.4 Trail Builder Service

Responsibility: Build correlation trails from the topology graph + trail policy. Produces overlapping, policy-bounded clusters; a device may appear in many trails.

Build instructions:

  • On topology.changed (or on demand), fetch the relevant graph closures from the Topology Service and the trail policy from the Knowledge Service.
  • Compute trails: transitive closure over dependency edges, bounded by IGP area; union SRLG members.
  • Persist trail definitions (members + the snapshotId); expose getTrailsForObject(managedObjectId) and getTrail(trailId).
  • Emit trails.built.

Technologies: Python; networkx (BSD) for in-memory closure; PostgreSQL for trail persistence.

Integrations: Consumes topology.changed, reads Topology + Knowledge; produces trails.built; serves Enrichment, Noise Filter, Pattern Miner, UI.

Acceptance criteria:

  • For the synthetic topology, a device on two LSPs and one SRLG appears in the expected multiple trails.
  • Trails are bounded per policy (no unbounded whole-network blob).
  • getTrailsForObject returns all trails containing the object.

6.5 Codebook Generator Service

Responsibility: Compile the codebook — enumerate candidate root-cause instances and generate each one's predicted symptom signature via forward propagation; tag scenarios to trails.

Build instructions:

  • Enumerate every graph instance whose type is in the fault-origin list (from Knowledge Service).
  • For each, run the propagation templates forward over the graph closure to collect the predicted symptom set (the codebook row), including the origin's own alarm.
  • Tag each scenario with the trail(s) its symptoms occupy.
  • Persist the codebook (scenarios + signatures + trail tags + snapshotId); emit codebook.generated.

Technologies: Python; networkx (BSD) for forward propagation; PostgreSQL.

Integrations: Consumes trails.built, reads Topology + Knowledge; produces codebook.generated; serves Pattern Manager (reconcile) and Correlation (match).

Acceptance criteria:

  • For the synthetic topology, the "fiber cut" scenario's signature matches the expected cascade; "line-card fault" and "port fault" are distinguishable (LOS / PortDown discriminators present/absent).
  • Every scenario is tagged to at least one trail.
  • Regenerating after a topology change produces an updated codebook tied to the new snapshotId.

6.6 Enrichment Service

Responsibility: First-stage alarm processing (used in both Phase 2 and Phase 3): normalization to the canonical alarm model, deduplication, deterministic noise filtering (flap-damping, self-clear suppression, maintenance suppression, known-chatter list), and trail tagging.

Build instructions:

  • Consume alarms.history and alarms.live.
  • Normalize to the canonical AlarmEvent (X.733-aligned fields).
  • Dedup repeated identical alarms within a short window (count-collapse).
  • Apply deterministic filters: suppress self-clearing transients below a hold time; flap-damp objects oscillating > N times/window into a single summary; drop maintenance-window and known-chatter alarms.
  • Tag each alarm with its trailIds via Trail Builder (getTrailsForObject).
  • Emit alarms.enriched (history) and alarms.enriched.live (live).

Technologies: Java (Spring Boot); stateless where possible, small windowed state for flap detection (in-memory or Kafka state store).

Integrations: Consumes alarms.*, reads Trail Builder; produces alarms.enriched, alarms.enriched.live.

Acceptance criteria:

  • Duplicates collapse; flapping reduces to a single summary; self-clear/maintenance/chatter are removed.
  • Every surviving alarm carries correct trailIds.
  • Same service instance works for both history and live inputs.

6.7 Noise Filter Service (DBSCAN)

Responsibility: Phase-2 statistical noise removal. Scope enriched alarms into per-trail windows and use DBSCAN to keep dense incident clusters and drop sparse outliers; output cleaned, trail-scoped groups for the Miner.

Build instructions:

  • Consume alarms.enriched (history).
  • Group alarms per trail within a coarse time window.
  • Feature-vectorize each alarm (timestamp, position in dependency graph, alarm type, severity).
  • Run DBSCAN/HDBSCAN per trail-window; keep dense clusters, label and drop noise points.
  • Emit cleaned, trail-scoped alarm groups as transactions.clean (raw groups; final session-window boundaries are the Miner's responsibility — see 6.8).

Technologies: Python; scikit-learn (BSD) DBSCAN, hdbscan (BSD). Stays a Python ML service.

Integrations: Consumes alarms.enriched, reads Trail Builder + Knowledge (DBSCAN params); produces transactions.clean.

Acceptance criteria:

  • A coincidental chatty alarm injected into a fiber-cut window is labeled noise and dropped.
  • The tight cascade cluster is preserved intact.
  • DBSCAN params are read from Knowledge Service (tunable, not hard-coded).

6.8 Pattern Miner Service

Responsibility: ML execution only. Assemble trail-scoped, session-windowed transactions and run PrefixSpan to discover frequent ordered alarm sequences with support/confidence/lift. Owns the mining model and its configuration. It holds no pattern state: no RCA, no codebook reconciliation, no explainability, no Pattern Store, no lifecycle — those belong to the Pattern Manager (6.9).

Build instructions:

  • Consume transactions.clean; finalize transactions using a session window (gap-based, per trail; gap is a tunable Knowledge-Service parameter).
  • Run PrefixSpan (Spark MLlib via PySpark) to discover frequent ordered alarm sequences; compute support / confidence / lift / conviction.
  • Expose mining configuration (min-support, max pattern length, gap/window constraints, max sequence count) sourced from the Knowledge Service — no hard-coded thresholds.
  • Attach mining provenance to each result (source trail, window reference, snapshot/codebook version in scope) so the Manager can do RCA and reconciliation downstream.
  • Emit raw mined sequences as patterns.mined (a PatternMinedEvent per sequence). Do not persist patterns or assign lifecycle.

Technologies: Python; PySpark / Spark MLlib PrefixSpan (Apache-2.0). Runs as a stateless Spark job.

Integrations: Consumes transactions.clean; reads Knowledge (mining params); produces patterns.mined for the Pattern Manager.

Acceptance criteria:

  • Given a transaction set containing the injected fiber-cut sequence, PrefixSpan recovers it as a frequent ordered sequence with correct support.
  • Spurious high-support / low-lift co-occurrences are surfaced with their lift so the Manager can flag them.
  • Mining thresholds are read from Knowledge Service; changing min-support changes the result set.
  • Each emitted PatternMinedEvent carries the sequence, support/confidence/lift, and provenance — and nothing about lifecycle or RCA.

6.9 Pattern Manager Service NEW

Responsibility: Own the full pattern domain — the Pattern Store, pattern status/lifecycle (draft → approved → deprecated), and all associated metadata: RCA, codebook reconciliation, explainability, and the human-approval workflow. This service deliberately contains no ML; it consumes the Miner's raw output and turns it into governed, reviewable, downstream-ready patterns.

Build instructions:

  • Consume patterns.mined (raw sequences + support/confidence/lift + provenance from the Miner).
  • RCA: map alarms → graph objects; the alarm whose object has no upstream dependency within the group (lowest in the dependency graph), corroborated by earliest timestamp, is tagged root cause. Where a mined pattern overlaps a codebook scenario, take RCA from the scenario.
  • Reconcile each pattern against the codebook: confirm matches, merge complementary appendages, flag patterns with no model explanation.
  • Explainability: assemble instance count, support/confidence/lift, timing (median inter-arrival, timeframe), codebook overlap, and supporting example incidents as pattern metadata.
  • Persist to the Pattern Store (PostgreSQL) with lifecycle draft; expose a read API for the UI; emit patterns.discovered.
  • Consume patterns.approved (from the UI) → transition lifecycle to approved and emit patterns.approved downstream for Correlation. Support deprecation transitions.

Technologies: Java (Spring Boot); PostgreSQL (Pattern Store).

Integrations: Consumes patterns.mined (Miner), patterns.approved (UI); reads Topology, Knowledge, Codebook; produces patterns.discovered, patterns.approved; owns the Pattern Store.

Acceptance criteria:

  • For a mined fiber-cut sequence, the service assigns correct ordering-based RCA and a codebook-overlap result.
  • Spurious high-support/low-lift co-occurrences are flagged via lift.
  • Each discovered pattern carries full explainability metadata and a lifecycle state.
  • Approval transitions lifecycle draft → approved and propagates patterns.approved; deprecation is supported.

6.10 Correlation Engine Service

Responsibility: Real-time correlation. Stateful matching of live enriched alarms against approved patterns and the codebook (partial/closest-match allowed); confidence scoring; conflict resolution; tag root cause + child alarms; persist incidents.

Build instructions:

  • Load approved patterns (Pattern Store + patterns.approved) and the codebook (codebook.generated), scoped by trail.
  • Consume alarms.enriched.live; maintain per-trail sliding-window state with timeouts.
  • For each window, evaluate:
    • Pattern match: advance per-pattern sequence state machines; fire when the match condition is met (partial allowed).
    • Codebook decode: score observed symptom set against trail-scoped scenarios using minimum-distance/closest-match (tolerate missing alarms, penalize spurious); pick best.
  • Conflict resolution: when multiple patterns/scenarios claim the same alarm, pick by specificity then confidence.
  • On a winning match: create an incident, tag the root-cause alarm, mark the rest as child alarms, persist to the Incident Store, emit correlation.results.
  • Keep the runtime window aligned with the Phase-2 session gap.

Technologies: Java (Spring Boot) with Kafka Streams (Apache-2.0) for stateful streaming; PostgreSQL (Incident Store).

Integrations: Consumes alarms.enriched.live, patterns.approved, codebook.generated; reads Pattern Store (via Pattern Manager), Codebook; produces correlation.results; owns Incident Store.

Acceptance criteria:

  • For a replayed fiber-cut storm, produces one incident with the LOS tagged as root cause and the downstream alarms as children — even with one trap dropped (partial match).
  • Multiple competing patterns resolve deterministically.
  • Alarm-reduction ratio and RCA accuracy computable against ground-truth labels.

6.11 Angular Web UI

Responsibility: Operator and engineer interface. One Angular application, four modules.

Build instructions:

  • Topology & trails module: organize topology by geo sites; zoom into a site to view site-level topology and toggle logical layers (fiber / IP / IGP / LSP / service); visualize trail clusters and highlight a device's multiple trails. Use Cytoscape.js (MIT) for graph rendering and MapLibre GL / deck.gl (BSD/MIT) for the geo view.
  • Pattern review & XAI module: list discovered patterns (from the Pattern Manager) with support/confidence/lift, RCA, timing, codebook overlap, supporting instances; approve/reject actions (emit patterns.approved to the Pattern Manager).
  • Config module: edit Knowledge-Service model parameters (DBSCAN, session-window gap, min-support, etc.).
  • Correlation stats module: live incidents, root-cause + children, noise-filter stats, alarm-reduction ratio, RCA accuracy — to demonstrate effectiveness.

Technologies: Angular 20 (MIT), Cytoscape.js, MapLibre GL/deck.gl; talks to a thin BFF or directly to service APIs.

Integrations: Reads Topology, Trail Builder, Pattern Store (via Pattern Manager), Incident Store; writes approvals (→ Pattern Manager) and config (→ Knowledge Service).

Acceptance criteria:

  • Geo-site view zooms into site topology with layer toggles and trail overlays.
  • Patterns can be reviewed with full explainability and approved/rejected.
  • Config edits persist via Knowledge Service.
  • Stats view shows reduction ratio and RCA accuracy for a replayed scenario.

6.12 Shared Canonical Event Library (build deliverable, not a runtime service)

Responsibility: Single source of truth for the event envelope and specialized payloads (§4.3); imported by every service.

Build instructions:

  • Define the envelope and payload models as the canonical contract. Ship two bindings generated from one JSON Schema: a Java library for the Spring Boot services (Topology, Knowledge, Enrichment, Pattern Manager, Correlation) and a Python/Pydantic library for the Python services (Simulator, Trail Builder, Codebook Generator, Noise Filter, Pattern Miner).
  • Include the PatternMinedEvent payload (raw Miner output) alongside PatternDiscoveredEvent / PatternApprovedEvent (Pattern Manager output).
  • Version with the repo; expose schemaVersion; provide (de)serialization helpers and validation.
  • Provide the shared managedObjectId scheme and the canonical AlarmEvent (X.733 fields).

Acceptance criteria:

  • All services import and validate against the library; the Java and Python bindings agree on the wire format.
  • Unknown major schemaVersion is rejected by consumers.
  • One change to a payload propagates to all services via the shared dependency.

7. Canonical Event Model (detail)

Envelope: eventId, type, schemaVersion, occurredAt, source, traceId, payload.

AlarmEvent (X.733-aligned): alarmId, managedObjectId, eventType, probableCause, perceivedSeverity, raisedAt, clearedAt?, state (raised/cleared), vendorRaw?, trailIds[] (added by Enrichment).

TopologyChangedEvent: snapshotId, changeType, nodes[], edges[] (typed).

TrailsBuiltEvent / CodebookGeneratedEvent: reference snapshotId; carry trail/scenario summaries (full data via API).

PatternMinedEvent (Pattern Miner → Pattern Manager): sequence[], support, confidence, lift, trailId, timing, provenance (source window, snapshot/codebook version). No RCA, no lifecycle.

PatternDiscoveredEvent / PatternApprovedEvent (Pattern Manager): patternId, sequence[], rootCauseAlarmType, support, confidence, lift, timing, codebookMatchId?, lifecycle.

CorrelationResultEvent: incidentId, rootCauseAlarmId, childAlarmIds[], matchedPatternId?, matchedCodebookId?, confidence, trailId.

Specialization rule: payloads share the envelope; each type maps to exactly one payload schema in the library.

9. Build Roadmap (walking skeleton first)

  1. Skeleton (one scenario end-to-end): Simulator (small topology + one fiber-cut scenario + IDs) → Topology Service (load into AGE, query) → Trail Builder (one trail) → Codebook Generator (scenarios) → Topology UI renders it.
  2. Learning slice: Enrichment (dedup/det-filter/trail-tag) → Noise Filter (DBSCAN) → Pattern Miner (session-window + PrefixSpan) → Pattern Manager (RCA + reconcile + XAI + lifecycle) recovers the injected pattern → Pattern UI approve.
  3. Real-time slice: Correlation Engine consumes live replay, matches approved pattern + codebook, emits one incident with RCA + children → Stats UI shows reduction ratio + RCA accuracy.
  4. Breadth: more scenarios, larger topology, more noise classes, multiple overlapping trails, conflict resolution, config tuning.
  5. Hardening: DLQs, idempotency, metrics dashboards, topology versioning edge cases.

Each step is independently demoable; do not start a later slice before the prior one passes its acceptance criteria.

10. Synthetic Data & Evaluation

The Simulator is the evaluation harness: every injected scenario carries a ground-truth {rootCause, children} label. Metrics to report in the Stats UI:

  • Alarm-reduction ratio — raw alarms ÷ correlated incidents.
  • RCA accuracy — fraction of incidents whose tagged root cause matches the injected label.
  • Noise-filter effectiveness — % of injected noise removed vs. real alarms retained.
  • Pattern quality — recovered injected patterns ÷ total injected.

Data realism requirements: X.733-shaped alarms, shared managedObjectIds, controllable timing jitter and noise mix, at least the fiber-cut, line-card-fault and port-fault scenarios plus 3+ noise classes.

Services whose core job is API, persistence, streaming or domain state run Spring Boot — Topology, Knowledge, Enrichment, Pattern Manager and Correlation Engine. The Topology Service stays on Spring Boot because the graph work lives in Apache AGE (openCypher), not in process.

Explicitly excluded: Neo4j Community (GPLv3), ArangoDB CE (BSL/restrictive since 3.12), SPMF mining lib (GPLv3), Confluent Schema Registry (community license), Grafana (AGPLv3), Redpanda (BSL).

12. AI-Led Build Guidance

  • Build one service per agent task, using its §6 spec as the prompt. Hand the agent: the service spec, the canonical event library (§6.12/§7), the relevant topic contracts (§8), and the acceptance criteria.
  • Build the canonical event library first — it is the contract every other service depends on.
  • Match the agent to the stack: the build now has a Python cohort (Simulator, Trail Builder, Codebook Generator, Noise Filter, Pattern Miner) and a Spring Boot cohort (Topology, Knowledge, Enrichment, Pattern Manager, Correlation) — route each to the appropriate specialist agent pool rather than a single generalist.
  • Enforce acceptance criteria as automated tests before integration.
  • Integrate along the roadmap order (§9); the Simulator's ground-truth labels are the integration test oracle.
  • Keep the Topology Service as the only component touching AGE; keep the Knowledge Service as the only home for authored templates/policy/params; keep the Pattern Manager as the only owner of pattern state — these boundaries prevent the architecture from rotting.
  • Defer (explicitly out of MVP): redundancy/protection-aware templates, closed-loop feedback execution, multi-domain, HA/scale.
