# Design Gaps — Data-Integration Verification
> Generated by the application-design synthesis + adversarial integration verification (28 data-exchange hops checked across P1/P2/P3). Each gap is a place where the data one service emits does not exactly align with what the consuming service (or frontend) expects, per the merged designs/schemas. Tracked here until resolved; fixes land in the owning service's spec/design via gated PRs and are reflected in `application-design.md`.
**Status:** CLOSED — all 24 original data-integration gaps + 1 transitively-surfaced (P2-GAP-10) resolved and merged (PRs #134–#144).

## Cross-cutting theme — canonical alarm-type token identity
The largest cluster (P2-GAP-01/02/03, P1-G5/G6, P3-G2, P2-GAP-04) is one root issue: the correlation chain needs **one consistent field carrying the alarm-type token** that is mined into `PatternMinedEvent.sequence`, baked into codebook scenario signatures, tagged as `rootCauseAlarmType`, and matched at correlation time. Today three value spaces compete: `AlarmEvent.eventType` (X.733 *category*, e.g. `communicationsAlarm`), `AlarmEvent.probableCause` (e.g. `lossOfSignal`/`linkDown` — what the frozen fixtures actually mine on), and Knowledge `alarmTypeVocabulary` (e.g. `LinkDown`/`FiberFault`). These must be unified into one join key before pattern↔codebook↔correlation matching can work end-to-end. This is a **contract-level decision** (event-model + Knowledge vocabulary + codebook/CE).
